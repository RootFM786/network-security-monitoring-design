# Telemetry Strategy

## Objective

The original design aimed to collect enough data to identify reconnaissance, suspicious access and anomalous network behaviour without attempting to capture everything everywhere.

## Data Types

### Full Packet Data

Full-packet data was treated as the most detailed source of evidence.

The design proposed collecting it selectively around critical server assets and during live incident investigation, rather than across the entire network, because of storage, processing and legal constraints.

### Session Data

Session data included communication metadata such as:

- source and destination IP addresses
- port numbers
- timestamps
- data usage

This was intended to support investigation of unauthorised connections and access to restricted resources.

### Statistical Data

Statistical telemetry was intended to help identify behaviour that deviated from normal traffic patterns.

Examples included:

- unusually high outbound traffic
- abnormal access frequency to sensitive resources
- unusually high DNS activity
- DoS-style traffic spikes
- unexpected increases in connected wireless devices

### Alert Data

Alert data represented events generated by IDS/IPS and other monitoring systems that required analyst review.

## Proposed Tooling

The design proposed an ELK-based monitoring stack using:

- Elasticsearch for search and analysis
- Logstash for data processing
- Kibana for visualisation
- Filebeat for log collection
- Winlogbeat for Windows event collection
- Packetbeat for network telemetry
- Auditbeat for audit-related host telemetry

## Design Principle

A key idea in the original report was **selective collection**: gather richer telemetry around critical assets and use lighter-weight data across the wider network to balance visibility against performance and storage constraints.
